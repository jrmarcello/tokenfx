## MUST FIX — token_prefix blast radius missed (highest-value finding)

The spec hashes `onboarding_invites.token` in place and adds a new `token_prefix` column (backfilled from plaintext pre-hash). It correctly updates `invites.ts`'s revoke path to use the new column, but **misses two other consumers that derive an 8-char prefix by re-slicing `.token` live** instead of reading the new column:

- `apps/server/lib/queries/manager-alerts.ts:138` (`loadFirstAutoProvisionAlert` JOIN: `eq(onboardingRedemptionLog.tokenPrefix, sql\`left(${onboardingInvites.token}, 8)\`)`) and `:228` (`acknowledgeAlert`'s `WHERE EXISTS` raw SQL: `JOIN onboarding_invites i ON r.token_prefix = LEFT(i.token, 8)`). Once `token` stores a hash, `LEFT(token,8)` stops matching `onboarding_redemption_log.token_prefix` (which manual-token redeems derive from the *plaintext* the caller submits, never from the DB column) — the manager "developer auto-onboarded via SSO" banner silently returns zero rows for **historic** pre-migration data, forever.
- `apps/server/lib/auth/sso-auto-provision.ts:295` (FOR-UPDATE re-select doesn't fetch `token_prefix`), `:364` (`tokenPrefix: fresh.token.slice(0, 8)` written into the redemption log), `:642`/`:649`/`:659` (same `.token.slice(0,8)` idiom for rejection-audit prefixes and a `logger.warn` field). All of these read `.token` from a DB row and slice it — post-migration this becomes a hash-derived prefix, which happens to still self-correlate for *new* sso-auto rows (both sides of any future JOIN are hash-derived) but permanently diverges from the plaintext-derived convention used everywhere else (manual-token redeem, `invites.ts` create/list/revoke, and any historic row).
- `apps/server/lib/auth/match-active-invites.ts` (`ActiveInvite` type + its SELECT) never projects `token_prefix`, so the fix requires threading a new field through this module before `sso-auto-provision.ts` can stop reslicing `.token`.

Net: 4 files, ~7 call sites, not currently in the spec's Files-to-Modify or Tasks (`TASK-3`'s file list mentions `sso-auto-provision.ts`/`match-active-invites.ts` but frames it as "verificar se necessário" — the Context section's own assessment, "usam a linha do invite como identificador opaco — hash serve," is correct for `revalidate-invite.ts` (confirmed: its `InviteRow.token` field is carried but never read by the predicate) but wrong for the `.slice(0,8)` call sites above). TC-I-10 ("SSO auto-provision continua funcionando") wouldn't catch this — the flow completes successfully, it just writes/joins on semantically wrong prefix data. Recommend an explicit TC seeding a pre-migration sso-auto redemption_log row (plaintext-derived prefix) and asserting the banner still surfaces it post-migration-0007.

## MUST FIX — `/api/manager` middleware matcher extension is a no-op under SSO mode as designed

`apps/server/lib/auth/auth.config.ts:153` — `authorized()`'s gate is `if (!path.startsWith('/manager')) return true;`. `/api/manager/dismiss-anomaly` does **not** start with `/manager` (it starts with `/api`), so extending only `apps/server/middleware.ts`'s `matcher` (the spec's plan) does nothing under `AUTH_REQUIRED=true` — the callback short-circuits to unconditional `true` before the role/session checks. The spec's Design section (`middleware.ts` bullet) never lists `auth.config.ts` as a file to modify, but `auth.config.ts` is the *only* place a NextAuth v5 `authorized()` callback can branch response shape (return `false` → redirect to signIn per the codebase's own comment at `auth.config.ts:155`; return a `NextResponse` directly → that response wins, as already demonstrated by the existing `/manager/admin` 403 branch at `:159-163`). Fix has to extend the path-prefix check to also match `/api/manager` and branch JSON-401 vs redirect-for-pages inside that callback — not in `middleware.ts`, which has no per-path hook into the delegated `NextAuth(authConfig).auth` call.

Also: the localhost-mode half of the matcher extension (DNS-rebinding gap, the actual LOW finding this task exists for) **is** correctly designed — `localhostMiddleware` in `middleware.ts` is path-agnostic and already returns JSON 403, so extending the matcher alone does fix that half.

Secondary: `apps/server/lib/auth/middleware.test.ts` tests an unrelated helper (`requireRole` in `lib/auth/middleware.ts`, used inside route handlers via DI) — NOT the root `apps/server/middleware.ts`. There is currently no test file for the root middleware or for `authorized()`'s path logic at all (`grep -r "authorized(" **/*.test.ts` → no hits). The spec's "verificar arquivo de teste existente" instruction points an implementer at the wrong file. The natural home for new coverage is `auth.config.test.ts` (already imports `authConfig`/`buildAuthConfig` directly — the callback is a plain function, callable with a hand-built `{request, auth}` stub, no NextAuth runtime needed).

## Verified correct — sha256 (not bcrypt) for the invite token

256-bit crypto-random entropy (`generateInviteToken` = `randomBytes(32).toString('hex')`) makes brute force infeasible regardless of hash speed — bcrypt's slow-hash property exists to defend low-entropy secrets (passwords) against offline guessing, which doesn't apply here. Stronger argument than the spec's own (latency-only) framing: the redeem lookup is `WHERE token = ?` (PK equality, `apps/server/lib/queries/redeem.ts:209`) — bcrypt's per-call random salt makes equality-indexed lookup *impossible*, not just slower; a fast deterministic hash is a structural requirement, not a preference. The codebase already documents this exact "why not bcrypt for a deterministic-lookup hash" reasoning twice (`apps/server/lib/auth/email-hash.ts:4-8`, `apps/server/lib/auth/bearer-auth.ts:16-24`) — the spec's one-line `hashInviteToken` arrow function should get a doc comment in the same style; SHOULD FIX, docs-only.

## Verified correct — hand-rolled `isLoopbackHost` in `lib/reporter/config.ts` (don't import `apps/server`'s `isLocalhostHost`)

`pnpm-workspace.yaml` only lists `apps/*` as packages; root `tokenfx` and `@tokenfx/server` are fully separate deployable apps with disjoint dependency trees (root has no `apps/server` workspace dependency, no `packages/shared`). Root `lib/reporter/config.ts` genuinely cannot import `apps/server/lib/auth/auth-required.ts` (which is also NextAuth/Edge-runtime-coupled, not a generic util). Duplicating the ~10-line loopback check is correct, not a smell. Do make sure the new implementation mirrors `isLocalhostHost`'s *exact-match* semantics (`apps/server/lib/auth/auth-required.ts:75-82`, `Set.has()` after stripping `:port`, including bracketed `[::1]`) rather than substring/suffix matching — that codebase already had to defend against `localhost.evil.com`-style bypasses once; don't reintroduce the class in the sibling app.

## MUST FIX — migration approach hedge is a false dichotomy

Spec Design (`.specs/security-hardening-lowsev.md:79`) proposes choosing between SQL `digest()` and "hash em JS linha-a-linha" in the migration runner at implementation time. `apps/server/lib/db/migrate.ts:117-120` runs drizzle-orm's `migrate()` against plain `.sql` files only — there is no hook anywhere in this runner for a custom JS-per-migration step (confirmed: no backfill-script precedent anywhere in `apps/server/`). `pgcrypto` is already enabled (`apps/server/lib/db/migrations/0000_init.sql:5`). The hedge should be resolved now, not deferred — commit to `encode(digest(token,'sha256'),'hex')` in pure SQL.

## SHOULD FIX — keep `token` name vs rename to `token_hash`

Recommend the rename. Precedent already exists in the same schema file: `secretHash: text('secret_hash')` (`apps/server/lib/db/schema.ts:80`) is this codebase's established naming convention for "column stores a hash of a credential, not the credential." The spec's stated reason for keeping the name (`.specs/security-hardening-lowsev.md:17`, "sem trocar PK") doesn't actually hold — Postgres `ALTER TABLE ... RENAME COLUMN` is metadata-only and automatically preserves any constraint (including the PRIMARY KEY) bound to that column; no FK anywhere references `onboarding_invites(token)` either, so there's no cascading cost. Not blocking — a legitimate "minimize diff" call if the team explicitly prefers it — but the given justification is wrong and shouldn't be the reason.
